# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **Every refusal code of the server has its text, 151 of them:** `app/src/main/assets/server-errors.json` now holds the 36 codes the server added for the laser, the pick-and-place machine, the board station, the CNC machine, the Gerber files, the CAM programs, the 3D printer, the slicer and the Moonraker and OctoPrint routes (an enclosure that is open, a latched machine, a heater that runs away, a printer that shows a certificate that is not the pinned one...), in English, Spanish, Italian, German, French, European Portuguese, Chinese and Japanese. `tools/gen_server_errors.py` writes the table, and `tools/server_errors_extra.json` keeps the rows of the eight newest codes for a checkout where Studio does not have them yet. New tests keep the table equal to the catalog of the server (they are skipped when the server folder is not next to this one) and keep the codes added after the copy of the catalog in the tests.

- **The machines of the plugins say they are a simulator:** the laser, pick-and-place, board, CNC, Gerber, CAM, 3D printer, vision and CAD machines of the server have only run against simulators, and the server says so in `detail` (`simulator_only`, `evidence`) and in the capabilities. The home page now shows a SIMULATOR ONLY badge on each of them and a line that says there is no proof on a real machine yet; nothing is shown in green for them.

- **Interlocks are in red and the emergency stop is one touch:** a machine held by a latch, by the latch of an emergency stop or by an alarm shows each of them as a red mark. A machine that can be stopped (an operator or an administrator, and the plugin has an emergency stop or a job runs on the machine) has a red button that stops at once with no question: the route of its own for the CNC machine and the printer (`/work/machines/{id}/emergency-stop`), the cancel of the job that runs for the others. A stop that gets no answer is sent once more, and one that never arrives is said plainly: use the physical stop.

- **The release of a latch is for administrators and asks twice:** a held machine shows the button to release the latch only to an administrator, whose touch opens a question with a second button; an operator or a viewer is told that only an administrator can do it. The routes are the ones of the plugins (`release` for the CNC machine and the printer, `laser/release` for the laser) and a refusal of the server is shown as it comes.

- **A print is started by a person, never by itself:** under each machine the app lists the jobs of its queue (running, held and waiting, from `GET /work/jobs`); a waiting job has Start and Cancel for an operator, each asking a second time, and a machine that is held cannot start anything. The 3D printer says that a person must start every print, and a machine that reports a queue that starts jobs by itself (`auto_start_queue`) gets a red warning: the app never switches that on.

- **The limits of temperature and the heaters of a printer are visible:** the card of a 3D printer shows the hottest the hotend, the bed and the chamber may be asked (a dash for a heater the printer does not have) and the temperature and target of each heater, as the plugin reports them.

- **An administrator sees the switches of the server that are off by default:** More lists, for an administrator, `mdns_announce`, `compat_api`, `compat_write` and `slice_enabled` with whether each is on (orange when it is looser than recommended) and what it does when it is on; they are changed in EH3D-STUDIO, never from the phone.

- **The new texts are in the 37 languages:** 32 phrases (the badge, the interlocks, the stop and the release, the queue, the temperature limits and the switches) in each of the 34 complete tables, written for each language and waiting for a review by native speakers.

- **34 more tests:** the rules of the safety of the machines (who may stop, release, start and cancel, the order of the interlocks, the alarm words, the limits and heaters, the queue, the switches), the routes the client uses for each plugin, a simulated server with a laser and a printer that latch when they are stopped and refuse the release to who is not an administrator, a queue that is only read until a person starts a job, and the contract of the table of refusal texts.

## [0.1.3] - Login that renews itself, sessions, retries, connection settings and every refusal code in eight languages

- **The login is renewed by itself:** the answer of the login now gives the id of the login and how long it lasts (`expires_s`); a request that finds the login in the last quarter of its life first renews it with `POST /auth/refresh` (once, and only for a person's login), a session kept from the last start is renewed when the app opens, and a refusal with 401 makes the client forget the token while a 403 keeps it. Signing out now uses `POST /auth/logout`.

- **The open logins are listed and can be closed:** More shows the logins of the person with their application and address (this phone is marked), closes one with `DELETE /auth/sessions/{id}`, and has a button that ends the login on every device (`POST /auth/logout-all`).

- **Every refusal of the server has a text in eight languages:** `app/src/main/assets/server-errors.json` holds the 143 codes of the catalog of the server in English, Spanish, Italian, German, French, European Portuguese, Chinese and Japanese. `tools/gen_server_errors.py` writes it from the catalog of the server and the `err_<code>` rows of Studio, so both say the same words; the 28 codes that Studio does not have yet (the laser, the pick-and-place machine, the 3D printer, the jog and the Gerber files) are in `tools/server_errors_extra.json`. The other 29 languages show the English text of a code that only this table has. A test fails when the table is not the catalog of the server (it is skipped when the server folder is not next to this one).

- **Time-out, retries and an optional search on the network are settings of the connection:** More has the time-out of each try (1 to 120 s, 15 by default), the retries after a failure on the network (0 to 5, 2 by default) and a switch for the search of the server on the local network, off by default. After a failure the client waits 200 ms, 400 ms, 800 ms... up to 2 s; a connection that could not be made is tried again for any request, a time-out or a 502, 503 or 504 only for the requests that do no harm twice, and a POST (a job, a login) is never sent twice.

- **The search for the server on the local network is optional:** with the switch on, the sign-in can look for `_eh3d._tcp` with the Network Service Discovery of Android for a few seconds and lists the IPv4 servers that answer; the person picks one, nothing connects by itself and the password is still asked for. It has not run on a phone.

- **The machines of the plugins are shown with their detail:** the home page lists the machines of the other plugins of the server (`GET /work/machines`, such as the laser, the pick-and-place machine and the printer) under the drilling and routing ones, with what each says of itself in `detail` and a red mark when it is latched by an emergency stop or an alarm.

- **42 more tests:** the simulated server of the app now renews and lists logins, ends them, is busy for a moment and can be told to fail a number of times, and the tests follow the renewal in the last quarter, the forgetting of a refused token, the retries and their pauses, the POST that is not sent twice and the connection that could not be made; the rules of the connection, the sessions, the machines of the plugins, the candidates found on the network and the table of refusals have tests of their own.

- **The texts of the new settings are in the 37 languages:** 12 phrases (the settings of the connection, the open logins and the other machines) in every table.

- **The login goes through the single login of the server:** the app signs in with `POST /auth/login` and says it is the `android` application, so the server keeps the application with the login and in its audit (it used the first, application-less route before).

## [0.1.2] - Newest improvements of the Android app

- **A stop that the ended session refused is sent again after signing in:** the machine ids are kept in memory only, for two minutes, so signing in late never stops a job that was started afterwards; the person is told at once that the stop did not arrive.

- **The warning that a drill file did not state its unit is written in the language of the app:** the server's `units_supposed` warning had no phrase of its own and showed as a generic server warning; it now has its text in the 37 languages.

- **A start-up with no link to the server keeps the saved session:** the session is deleted only when the server itself refuses it (401); a server out of reach, an error of the server or the page of another service on that address leaves it in place, says there is no connection and tries again with growing waits.

- **The update checks the SHA-256 that the release publishes for the APK:** the downloaded bytes are hashed while they are written and a file that does not match the published digest is deleted and refused before it is looked at as a package (a release that publishes no digest is checked as before: package name, version code and signing key). Tests cover reading the digest and the comparison.

- **A stop that is refused because the session is no longer valid says so, and "stop all" reaches every machine:** the plain notice that the stop did NOT arrive is shown before the app returns to the sign-in, and the stop of the whole fleet is sent to every machine the fleet lists, not only to those that were working at the last reading.

## [0.1.1] - The release carries its APK again

- **The release asset `EH3D-ANDROID-CONTROL-release.apk` is attached again:** 0.1.0 was published without it and the in-app update could not find the file; the app now finds it in this release and can update.

- **A reply that is not JSON is the wrong server, not a lost connection:** `classifyFailure` now checks the `bad_json` code before the status, so a body that is not the JSON of EH3D-SERVER is told as another service on the address even when the client could read no status from it (the old order called it no connection). The test that fixed the old behaviour is changed and the case is added to the scenarios of the simulated server.

- **Simulation of the server for the app:** add `app/src/test/java/es/electrohobby3d/eh3d/SimulatedServerTest.kt`, a simulated EH3D-SERVER of this computer that remembers who is signed in, shows one machine with one job and can be made to fail: the link dropped, another service on the address, a 503, a restart that forgets the sessions, a stop that takes a moment to reach the machine. A phone that looks at the fleet every second and a half with the real client and the real rules of the link and of the stops (the clock is a number, so nothing waits) shows what the screen would say at each step. Eight tests cover the blink and the no connection with the waits that grow, an answer called old, the wrong service, the 503 and the 404, the sign-in again after a restart, a stop that is confirmed, a stop that never reaches the machine and the notices after an outage. Nothing has run against a real server or a phone. The same scenarios are still to be written for the iPhone app.

- **A floor of coverage in the CI:** the build stops when the tests cover less than 70 % of the lines of the code that holds rules (the model, the client of the API, the update, the address, the session and the languages; it is 72 % today, it was 66 % before the last tests) or less than 20 % of the whole app, whose screens cannot be run on the JVM.

- **75 more tests, a check that the two phone apps agree and a measure of coverage:** the client of the API is tested against a server that lives in the test (paths, methods, headers, bodies, refusals, a service that is not JSON, a server that is away), the readers of the answers of the server are tested from their edges (what is missing, null or from an older server), `tools/check_app_parity.py` fails when the examples of the answers, the catalog of the refusals or the tables of the 37 languages differ from the ones of the iPhone app, and the CI prints how much of the code that holds rules the tests cover (`tools/check_coverage_floor.py`).
- **The build tools and libraries are updated:** the Android Gradle plugin 9.5.1, Kotlin 2.4.21, Gradle 9.9.1, coroutines 1.11.0, WorkManager 2.12.0 and the JSON test library, with the tests, the lint and the debug APK of the CI passing.

## [0.1.0] - Safer remember-me and sign-out and the current refusal catalog

- **The shared validation tools are updated:** the validator also runs the workflow and lessons checks of the suite with their latest rules, including a check to run before every push.
- **The debug APK of the CI is kept for 30 days:** the upload step names its retention (`retention-days: 30`) like the release workflow, and the repository's own retention of artifacts and logs is 30 days instead of 90.
- **The CI validation checks the workflows and the lessons of past CI failures against a baseline:** `tools/workflow_hygiene.py` and `tools/lessons_lint.py` (copies of the shared tools) run in the validation, and only findings that are not in `tools/workflow_hygiene_baseline.json` and `tools/lessons_lint_baseline.json` fail it, so what exists today stays as it is and a new one is caught. `python tools/workflow_hygiene.py --root . --detail` and `python tools/lessons_lint.py --repo .` list the findings.
- **The validation of the CI is the reusable one of the documentation hub:** the job `validate` calls `validate.yml` of EH3D-DOCS (pinned by commit) and what the repository checks besides it is in jobs of their own, with the check of the CHANGELOG.
- **Signing out is tested against a server on the same computer:** the call that ends the session is a POST to `/api/v1/logout` with the token that is being closed, and a server that is down or refuses the token never breaks the sign-out.

- **The catalog of the refusals of the server is the current one:** the copy that the test reads has the 115 codes of the server (it had 89), and the 26 new ones are listed with their reason: the files of a project, the catalogs, the plugins, the design program and the switches of security have no page in the app, and the message of the server is shown as it comes for the refusals of a rack, of a plugin and of too many listeners.
- **"Remember me" keeps only the session token:** the user and the password are never kept; with the box ticked (off by default) the token of the session is sealed in the Android Keystore and expires 30 days after the sign-in, signing out revokes it at the server and forgets it, and what an earlier version kept (the user and the password) is deleted at the first start. A token made before the expiry existed is dropped once. The two captions of the sign-in screen are in the 37 languages.

## [0.0.9] - 37 languages, the person who started a job on its page and a text for every refusal of the server

- **37 languages:** the app speaks the 37 languages of the EH3D programs on the computer, in the same order: the eight it had (English, Spanish, Italian, German, French, European Portuguese, Chinese and Japanese) and Bulgarian, Croatian, Czech, Danish, Dutch, Estonian, Finnish, Greek, Hungarian, Irish, Latvian, Lithuanian, Maltese, Polish, Romanian, Slovak, Slovenian, Swedish, Norwegian, Icelandic, Ukrainian, Russian, Serbian, Albanian, Catalan, Galician, Basque, Brazilian Portuguese and Canadian French. The list of languages scrolls, the language of the phone picks a variant by its region (`pt-BR`, `fr-CA`), and the tests and `tools/i18n_check.py` check that every table has every phrase, with the same holes and no blank or English-only text. None of the 37 is written right to left.
- **The page of a job says who started it** as well as who stopped it, with the text the machine page already uses.
- **Every refusal of the server has a text in every language of the app:** 31 more codes of the catalog of the server (the tuning, the G-code, the ids, the LED ring, the updates, the jobs and the machines among them) say what went wrong in the language of the app instead of the raw message; a test fails when a code of the catalog has neither a text nor a stated reason (the refusals of files that carry the message of the server, and the codes of the design programs the app never asks for).
- **The case files shared with the iPhone app are checked in CI:** `tools/check_shared_cases.py` compares them with the ones of the other repository (the sibling folder, or the public one on GitHub) and fails when one differs, is missing or cannot be read; its own test runs before it.
- **Brand:** Add the application icon and the logos of the program.
- **A watchdog for the manual build:** `.github/workflows/build-watchdog.yml` looks every hour for a build that stays queued or running longer than the limit in `.github/build-watchdog.json` and opens (or updates) an issue `build-stuck`, which it closes when no build is stuck.
- **The release APK is built in GitHub Actions:** `.github/workflows/apk-build.yml` (manual, owner only) builds it with JDK 21 and Gradle without any cache, checks the application id, the version name and a version code that rises, writes `SHA256SUMS`, a build manifest and a provenance attestation, and opens an issue `build-failed` when it fails; the APK leaves unsigned and is signed on the maintainer's computer. See `docs/BUILD.md`.
- **Shared checks updated:** the validator also compares the badge and the Version row of the README with the manifest, fails when one of its checks cannot run, and the CHANGELOG step of the workflow reads the base branch from the environment.
- **More tests:** the preparation of a job, the link, the stops, the drawing and the summary from their edges, the tags and the releases of the update channel, and the addresses an operator types.
- **A version tag with a number too big for an integer is refused** instead of ending in an exception, and an address with a port that does not exist (0 or above 65535) is no longer accepted.
- **The workflows are hardened:** every action is pinned by its commit with its version in a comment, and the checkouts keep no credentials.
- **More tests of the update channel:** which tags are versions, which release is newer and which link of the APK is accepted.

## [0.0.8] - Summary before a start, an honest link and shared test cases

- **A summary before a job starts:** the dry run of the exact plan (how far each axis goes, the steps and the time) and the warnings of the server (a work that looks tiny, too big, far from the corner, stretched or past the course of an axis) are read, and Start shows what the job does, how long it takes, how far each axis goes and what looks wrong, with Start and Cancel; a setting turns it off (on by default) and then Start only asks once more.
- **The refusal `outside_course` has its own clear text** in the eight languages (the plan takes an axis past its course; move the work on the table or let the machine's tuning warn).
- **The state of the connection is told honestly:** connected, data that is getting old (with its age after five seconds), no connection only after two failures in a row (one blink of the Wi-Fi no longer shows it), and an address that answers another service; the retries slow down from 1.5 s to 10 s while the server is away and a button tries again now.
- **Pressing the stop without a connection warns** that the order may not arrive and to use the physical stop of the machine; a stop that did not reach the server says so plainly, and after a stop that did, the app says it was sent, then confirmed or that the machine still works.
- **Case files shared with the other phone app:** the summary, the link, the failures, the stops, the notices, the addresses and the fields of the answers are tested from the same files in both apps, and a field that the server adds to its examples fails the test until the app reads it or says it ignores it.
- **A job says who started it and who stopped it:** the page of a job shows who stopped it (the server now sends both names).
- **Differences between the two phone apps are written down** in `docs/PLATFORM_DIFFERENCES.md`.
- **The answers of the server are read in the tests from its own examples:** the fleet, the jobs, a job, the preview, the spindle and an error are the files that the tests of the server make, so a change in the answers that the app does not follow fails here.
- **Issue forms and a pull-request template:** the repository now has the bug report (it asks for the versions that `eh3d-updater --cli status --offline` lists), documentation, improvement and hardware validation forms (with the machine used) and the pull-request template of the suite.

## [0.0.7] - The release no longer closes when it starts

- **The app closed at once when it started (version 0.0.6, the installed release):** the periodic watch of the fleet brought WorkManager, which keeps its jobs in a database that is made by reflection through its empty constructor; the shrinker of the release removed that constructor, so the app failed before it drew anything. The constructor is kept now. The debug build is not shrunk, which is why the tests did not show it.
- **The CI builds the release too and checks it:** `assembleRelease` runs besides the debug build, and `tools/check_release_build.py` fails when the shrinker removed the empty constructor of a generated class (`*_Impl`), the failure that closed the app.

## [0.0.6] - Starting a job asks once more, the emergency stop asks the server to stop the machine and signing out closes the session

- **Starting a job from its page asks once more** (check that the machine is prepared and clear), as it does from Prepare, with the same words in every language; a touch by mistake no longer sets the machine going.
- **The emergency stop asks the server to stop the machine** (`POST /machines/:id/stop`), whether or not the app knows which job runs on it, and shows the error if it did not get there; the camera asks for a one-use ticket instead of putting the token of the session in the address.

- **Notices with the app closed:** a periodic job (WorkManager, every 15 minutes at best) asks the server with the session kept in the vault and tells a machine that waits for the operator or a job that ended; signing out stops it. The rule that decides what is told is one function used by the screen and by the job.

- **An answer that is not JSON** (another web service at the address) is an error on the screen, not a crash.
- **Signing out closes the session on the server** (the call goes with the token that is being closed), and a slow refresh of another machine no longer paints its spindle or sensors on the page of this one.
- Clearer messages for a wrong setup code, a weak password and a bad name, in the eight languages.

## [0.0.5] - Resume a stopped job and the GRBL switch in read only

- **Go on from where a job stopped, with the file the server kept:** a job that failed or was cancelled (drilling, routing or G-code) has a button that asks the server (`resume-from`) for a new job made from the saved request, with the holes, paths or lines already done left out; the file is not picked again. The new job opens on its page, ready and never started, and says which job it goes on from. Messages for the new refusal `not_stopped` and for the new texts in the seven tables of languages. - 2 tests more (the job that can be gone on from and the switch), written and not run.

## [0.0.4] - Prepare a job, G-code jobs and the sensors of the drill head

- **Prepare job:** the page of a free machine has a Prepare job page. Choose what is done (drilling, routing, both or a free G-code program; a machine takes only what its connection allows), pick the file with the system file picker (the server has no list of files, so the text of the file is sent in the request that plans the job; an optional tool table can be picked too), and the server plans it without creating anything. The page lists the tools of the file in the order the job does them, with the count of holes or paths, the diameter when an Excellon file declares it and the spindle speed; switch tools off (`skip_tools`) or start at one tool (the ones before it in the order of the job are left out, as in BUNGARD-GUI); the spindle warnings of the plan are shown. Start asks for a confirmation, creates the job and starts it. With both, a drilling job and a routing job are created and the first starts; the second stays ready in the Jobs tab, because a job never starts by itself.
- **G-code jobs:** pick a G-code file and create a `gcode` job on a machine whose connection is the simulator or GRBL; the page shows the lines that will be sent, the area and the estimate. A running G-code job can be paused and resumed (the held wait and the wait after a stop both say what they are), cancelled, and a failed or stopped one can be continued from the line it reached (`skip` with the `line` of the job; the same program is prepared again, asking for the file when this session does not have it, and the machine waits for the confirmation before its first move). The spindle and the coolant are started again only with the switch "start the spindle and the coolant again", which is off by default.
- **Messages and help:** new messages for the refusals of the server when preparing a job (`bad_gcode`, `bad_ncd`, `unknown_tool`, `bad_tool`, `out_of_table`, `wrong_machine`, `too_big`, `not_pausable`, `not_in_state`), a help topic for the page and 53 phrases in the seven tables of languages.

## [0.0.3] - Spindle of the machine, tools switched off in a job and the sensors of the drill head

- **What the sensors of the drill head say:** the card of the head shows how the last reading of the laser went (valid, weak signal, too much spread, out of range, sensor fault) with the distance, how long ago it was taken and the offset the laser was calibrated with; whether the pulses of the speed sensor are clean or noisy and how many were refused as noise; how many temperature sensors the node found on the wire, with a warning when it only guesses which one to read; and the version of the node. A node that does not say (an older one) shows nothing of this. 17 phrases in the seven tables of languages. The settings of the image of the camera, the calibration of the laser and the choice of the temperature sensor stay in the panel of the node: the server does not hand them on yet.
- **The spindle of the machine:** the page of a machine shows which spindle it carries (the original one or the one with a variable-frequency drive, or none), its limits and the top speed the node should be set to; an administrator chooses the spindle and what the server does with a job that asks for more (refuse it, or let it through cut down to the top of the spindle). A job shows the excesses it was let through with, the tools that were switched off for it and the holes or paths already done that it leaves out. The messages for a job refused by the spindle or left with nothing to do are in the eight languages. Choosing a drilling job, a routing job or both, and switching tools off, is not here: the app does not prepare jobs.
